# AGENTS.md

## What this repo is
Workspace for **AI-generated three.js scenes/animations** (施工场景 was the first domain, not the only one). No build/test/lint/CI config and no package manifest — just git plus the files below. Commit style is `feat|fix(battle): 中文描述`.

- `threejs-施工场景动画-提示词规则.md` ← construction domain source of truth + copy-paste prompt templates.
- `threejs-场景动画-提示词模板与编写技能.md` ← generalized 10-section prompt structure (`+模拟契约/验收接口`), the `R1–R10` rules for **real-time/emergent** scenes (crowd combat, crowds, traffic), WebGPU/WebGL r185 pitfalls, the verification recipe, and measured perf budgets. **Read this before writing a prompt for anything that is not a fixed procedure.**
- `threejs-提示词记录.md` ← chronological log of the user's own prompts, grouped by session with a git-commit mapping. A historical record, **not** a rule source — don't treat its wording as binding.
- `civil-war-battle.html` ← worked reference: 南北战争 group combat with 战壕/高射炮/战斗机/轰炸机 and a 一战 armour layer on top (three r185, single file). At `S = 4` scale it carries 2×8 infantry + 2×2 cavalry + 2×2 batteries + 16 AA guns + 14 aircraft + 10 tanks + 6 trucks + 4 motorcycles over a 3.1 km field, with trenches, airfields (sortie cycle), ~1100 obstacles, instanced billboard VFX and bloom/grade post-processing. Emergent outcome, deterministic (`?pause=1`), `?fx=0` disables post-fx, `?webgl=1` forces the WebGL path, `?anime=0` disables the Anime.js layer, `?nohud=1` runs headless-of-UI. The premise is deliberately anachronistic — do not "correct" it.

The rules below are the ones agents most often get wrong; they generalize from that research to **any** three.js scene. Don't re-derive them.

## Symptom → cause index (check these first)
| Symptom | Look at |
|---|---|
| A group of meshes vanishes as the camera moves | §Draw-call "stale `InstancedMesh` bounds" — dynamic instanced meshes need `frustumCulled = false` |
| A mesh is in the scene, matrices correct, nothing on screen | §Air: `mats[def.mat]` — a material *string* makes three skip the mesh silently |
| One element occludes half the frame | §Visibility cause 1 — spectator camera inside the traffic lane / cruise altitude |
| Distant geometry "reads as sky" | §Visibility cause 2 — `fogNear` inside the play area |
| A ground decal flickers or disappears | §Visibility: coplanar decals need `polygonOffset` |
| A ground decal is invisible inside a trench/on a berm | §Anime.js: decals must sit on `groundY()` (walkable surface), not `terrainH()` |
| Two ground decals stack in the wrong order | §Anime.js: `polygonOffset` only orders against the ground — decal-vs-decal needs `renderOrder` |
| Anime.js `animate(light, …)` silently does nothing | §Anime.js wiring: the core and `adapters/three` must resolve the *same* module graph, or they use two different registries |
| A feature exists but changes nothing | §Working method — its *attribute* is not wired into the simulation |
| Retuning a visual changed the battle outcome | §Effects: PRNG separation; run the three probes |
| Units jitter on the spot / flip orders every tick | §AI: key alternation off roster parity, not the per-tick sorted list |
| Units frozen in `charge` with an unchanged headcount | §Rescale: rout speed ≥ charge speed (infinite chase) |
| Melee grinds for minutes on a wide front | §Rescale: missing rout cascade |
| Vehicles/wheels swing around the chassis | §Armour: one rig part per axle, origin on the axle line |
| Reinforced soldiers overlap living men | §Armour: `kill()` compacts the slot registry — re-register a free slot |
| `mergeGeometries` returns null / throws in `updateMorphTargets` | §Budget: mixed index state — `toNonIndexed()` first |
| Frame cost jumped after enlarging the map | §Rescale checklist (fog, shadow mapSize, segments, counts) |
| A camera view "shows nothing / only grass" | §Motion: `OrbitControls` only `update()`s on pointer events — call it after moving the camera |
| One soldier dying blooms into an orange fireball | §Motion: `flashPool` is HDR (2.4) and crosses the 1.3 bloom threshold — never use an additive pool for hit sparks |
| Draw-call count differs between two builds *at the default view* | §Motion: a now-correct camera aim legitimately sees more objects; compare budgets from an all-visible camera |
| 机场/道路/河道在画面里看不见 | §Terrain: 共面贴花缺 `polygonOffset`、跑道与草同亮度、`fogNear` 在内容之内、`anisotropy=1` |

## General three.js generation rules (any scene)
- Lock `three` ~r185+; use `renderer.setAnimationLoop` + `Timer/Clock.getDelta()`; **never** frame-rate-dependent `+= constant`. Handle window resize.
- Scaffold predefines `scene` / `camera` / `renderer` / `controls`; do not recreate them. Output runnable JS; no Markdown in generated files.
- Renderer: try `WebGPURenderer`, fall back to `WebGLRenderer`; `setPixelRatio(Math.min(dpr, 2))`; `ACESFilmicToneMapping`; `PCFShadowMap` (**`PCFSoftShadowMap` is deprecated in r185**).
  The WebGPU build does **not** export `WebGLRenderer` and rejects `ShaderMaterial`/GLSL — pick the build at load time (inject the importmap from a boot script after probing `navigator.gpu`, on `DOMContentLoaded`), and use canvas textures + standard materials only.
- Ground = large `PlaneGeometry`; **object** size `0.5–5 m` (large scene extent is fine — spread by coordinates, never by root scale); every mesh `castShadow = true`, ground `receiveShadow = true`.
- Sun `DirectionalLight` needs **explicit shadow-camera bounds** sized to the *max activity radius* (not the initial layout) + 2048 map; add `HemisphereLight` + small ambient. Shadow texel = `2×halfExtent/mapSize`, so sub-0.2 m props get no usable shadow at ±170/2048.
- Build in passes, never one-shot: `blockout → structure → form → material → lighting → interaction → optimization`. Spec non-trivial scenes before writing code.
- Prefer code-only geometry: primitives / `Shape` extrude / curve `tube` / displacement / canvas textures. No external model dependencies unless asked.
- Repeated parts → `InstancedMesh`. Only sync/update objects that actually moved. Use deterministic seeds for procedural noise — and **separate the gameplay PRNG from the visual-effects PRNG**, or retuning smoke will change the outcome.
- Root container `transform.scale` must stay `[1,1,1]`; hide nodes with transparency, not scale (scale-0 **instance matrices** are the correct way to hide individual instances).
- Adjacent parts must physically connect/overlap `0.02–0.05` at seams (no floating parts).
- Avoid flat 2.5D slabs; verify with a distinct-Z count (planar extrusion ≈ 6–10 planes, real volume > 11).
- Describe form with 3D terms, never "nice/smooth/shiny".

## Motion / animation rules (any scene)
- Model motion as an explicit state machine; interpolate with per-axis speed-limited easing, never teleport or linear snap.
- Push driven bodies `kinematic → dynamic` when released, so gravity/contact resolves naturally.
- Fixed physics `timestep = 1/60`, cap ≤ 8 substeps/frame; count durations in **physics steps/timers, never wall-clock** (`Date.now()` breaks under variable speed).
- "有 clip ≠ 会播放": a `mixer` + action alone proves nothing — sample actual transforms at a time and compare to the track value.
- **Tracking a moving target** (formation slot, hook, attach point): the stop dead-zone must be **smaller than the target's per-frame displacement** (`v·dt`). A dead-zone of 0.22 m against 2.8 m/s @ 60 Hz (0.047 m/frame) makes agents stutter (stop 1 frame in 4); if the speed cap is also ≤ target speed they fall behind permanently. Use ~0.02 m.
- **Never milestone on an absolute coordinate** (`Math.abs(cz) > 6` is already true at spawn). Use a signed/directional form (`cz * toward > 6`) or a distance.
- **Morale: accumulate-and-decay, with dual rout thresholds** — permanent shock (e.g. from ranged fire) makes units break the moment melee starts. `morale = 1 + resolve − 1.65×lossRatio − shock`, `shock` capped and decaying, rout on `men<30% || morale<0.22`.
- **Effects budget = radius × lifetime × opacity**, not count. Smoke ≤6 m / ≤2.5 s / ≤0.5 opacity; a paused sim freezes every effect at peak, so screenshots exaggerate long lifetimes.
- **`OrbitControls` only calls `update()` from its own pointer handlers.** Writing `camera.position.set(...)` + `controls.target.set(...)` moves the camera but **never re-aims it** — every static "机位" silently kept the orientation from the previous frame (the overview showed nothing but grass), and follow/orbit views translated without turning. Call `controls.update()` after any programmatic camera move, and once per frame for follow/orbit views. Diagnose with a screenshot per view, not by reading the position: the position was exactly right while the aim was wrong.
- **A camera tween must yield to the user and must not be the only path.** Snapshot `{p0, t0, fov}` into a state object, animate one scalar `k: 0→1` (`inOutQuart`, ~0.95 s) and `lerpVectors` + `updateProjectionMatrix()` + `controls.update()` in `onUpdate`; `cancel()` on the controls' `start` event. Keep an `instant` overload for the debug API (`camera(id, true)`), or two screenshots of "the same view" are not comparable.
- **Shake must not leak into the camera's real state.** Add the offset to `camera.position`, `lookAt(target)`, render, then restore both the position and the saved quaternion — the camera is render state, not sim state. Scale amplitude by `power / (1 + distance/70)`: a distant battery that shakes the frame as hard as a near miss is worse than no shake.
- **Screen-space punch is three cheap knobs**, all driven off one `impactFeedback(power, x, z)`: camera shake, a short `toneMappingExposure` punch (1.12 → 1.12+a → back), and a radial DOM flash opacity. They read as "impact force" far more than a bigger particle does.

## Anime.js 动效层 / 血肉 / 弹药冲击力 (verified in `civil-war-battle.html`)
- **Wiring (v4.5+):** map `animejs` → `…/animejs@4.5.0/dist/modules/index.js` and `animejs/adapters/three` → `…/dist/modules/adapters/three/index.js` in the injected importmap, then `await import()` inside `try/catch` so a CDN failure degrades to instant snaps instead of killing the scene. **Both entry points must come from the same module graph**: the adapter registers into `dist/modules/adapters/registry.js`, and the core's `animation.js` resolves through that same registry — pairing the single-file bundle (`+esm` / `anime.esm.min.js`) with the adapter subpath gives you *two* registries and `animate(light, …)` silently does nothing.
- **The three adapter duck-types `isObject3D / isMaterial / isFog / isColor / isVector* / isUniformNode`.** `renderer`, `EffectComposer` and `UnrealBloomPass` are none of those — tween a plain `{v}` proxy and assign in `onUpdate` for exposure/bloom, and use the adapter for what it is for (Light intensity/color, `scene.fog.color`). Verified: `ux().adapter === true`, and the end-of-battle dusk timeline moves `sun.intensity 2.6 → 1.75` and `fog #cdbfa2 → #c49b74`.
- **Keep the whole motion layer off `rnd`/`vrnd`.** Anime.js drives DOM/`k`/exposure on wall-clock; nothing in it may touch the gameplay PRNG. Verified: `?anime=0` (and `?nohud=1`) leave the gameplay hash byte-identical *including particle counts*.
- **Blood & gore hang off the single casualty choke point.** `kill(s, hx, hz, force)` is the only place a soldier dies (volley / shell / fragment / cavalry impact / melee / bomb), so one hook covers every weapon; `hx,hz` is the projectile direction (radial from the blast centre when there is none). Layer = premul dark-red mist (`maxSize 2.6`, `ttl 0.30–0.52`, `o0 0.62` — keep it thin or it reads as a red flower) + a gravity droplet pool (`buoy −15`, 4–8 per death) + a 26 %-chance blood stain decal on the ground.
- **Never emit a hit "spark" from `flashPool`.** It is HDR (~2.4) and crosses the 1.3 bloom threshold, so one death blooms into an orange fireball and ten simultaneous deaths look like napalm. Blood reads through its own dark red, not through glow.
- **A ground decal must be placed on the surface the actor actually stands on — `groundY(x,z)`, not `terrainH(x,z)`.** `groundY = terrainH + max(workH, obstacleH)`, and the trench ribbon is opaque at `terrainH + 0.04 … +1.30`; a stain placed at `terrainH + 0.02` is depth-rejected and never renders, which silently kills the effect in exactly the place the infantry dies (they deploy into the ditch). On open ground the two agree, so this only shows up as "it works in the meadow, not in the trench". Measured, not eyeballed: `ux().stainLift` (max `y − terrainH` over the decals placed so far) is **0.000** with the `terrainH` version and **0.413** in an ordinary battle / **1.208** when firing at the parapet line with the `groundY` version — same 70 stains, same seed. The blood *droplets* are 3D particles and render either way, so a screenshot of "red splotches in the ditch" does not prove the decals work.
- **Decal-vs-decal order cannot be expressed with `polygonOffset`.** Two `transparent` `depthWrite:false` instanced decals at the same world origin tie on `renderOrder`, then on depth, then fall back to `a.id - b.id` — so the later-created one always draws on top, whatever the offsets say. Set an explicit `renderOrder` (stain −1 / scorch 0 / crater 1). `polygonOffset` only orders a decal against the opaque ground.
- **Guard the phase you actually need.** `kill()` sets `state = 'gone'`-adjacent fields before calling its effect hook, so a `state === 'gone'` test inside the hook can never fire — `aliveSoldiers()` filters on `alive` only, so a departed soldier *can* still be picked as a casualty. Capture the pre-death state in the caller (`const wasGone = s.state === 'gone'`) and branch there.
- **WebGPU has no per-instance alpha for premultiplied pools** (`onBeforeCompile` is ignored) → the mist sits at full texture alpha until `ttl` and reads as a black ground stain. Scale the mist texture alpha harder than the general `FXA = 0.5` fallback (0.8 → 0.36 here).
- **"Ammunition impact force" is three separate reads, all cheap:** (1) a row of impact dust kicked up along the target line and just beyond it at every volley — without it a volley only shows muzzle flashes and you cannot see *where* it landed; (2) tracers that die on the ground/parapet (`t.y <= groundY()`) with a dust puff + 1–2 ricochet sparks from `shardPool`, instead of silently expiring in mid-air; (3) a low-angle dirt ring around shell/bomb/crash craters so the burst reads as "dug out" rather than "puffed up".
- **Cost of the whole layer: 5 draw calls.** Same camera, same t, all-visible: `fx(false)` 398 → **403 calls** / 1.115e6 → **1.118e6 tris** (t=0); with the composer at t=30: 426 → **431 calls** while live particles go 1133 → **1234** — 2 pool `InstancedMesh`es + 1 stain `InstancedMesh` + their transparent pass, and particle count is free.

## Effects layer (verified in `civil-war-battle.html`)
- **Never use `THREE.Sprite` for particle effects** — sprites do not batch (~1.1 draw calls each; 333 live smoke puffs = 705 calls total). Use one `InstancedMesh` of `PlaneGeometry(1,1)` per texture/blending group, billboarded each frame with `camera.quaternion * spinQuat`, `frustumCulled = false`, `instanceMatrix.setUsage(DynamicDrawUsage)`. 6 pools (flash/smoke/burst/dust/boom/mote) = 6 draw calls total, regardless of how many particles are alive.
- **`instanceColor` scales rgb only — it cannot fade alpha.** For additive pools that is enough (fade = `instanceColor = a × hdr`). For **normal-blend** smoke/dust it is not: a "faint" puff still occludes at full `map.a` and the occluded pixels are replaced by near-black, so dust reads as dirty black smears. Two rules: (1) use premultiplied `CustomBlending` (`blendSrc: OneFactor`, `blendDst: OneMinusSrcAlphaFactor`), and (2) make alpha actually per-instance, via `mat.onBeforeCompile` doing `vFade = instanceColor.r;` in the vertex stage and `diffuseColor *= vFade;` in the fragment stage (scales rgb **and** a — do not scale rgb alone). `mat.customProgramCacheKey` keeps the patched programs apart.
- **Smoke must be darker than the sky, and premultiplied maths decides how dark.** A bright overcast sky sits near linear 0.88; a puff whose texture rgb is 0.84 composites to ~1.0 and simply vanishes. Give powder smoke a mid-grey base (~0.6) with a top-lit/bottom-dark `shade` term so the underside still reads against the sky. Sanity check after any palette change: covered area should get *darker*, not brighter, as layers stack.
- Hide a dead instance with a **scale-0 matrix** and re-write its matrix only once (track `drawn`), not by `visible = false`.
- **Bloom needs HDR emissive, not a low threshold.** A daylight scene sits at linear ~0.7–1.3, so `threshold 0.82` blooms the whole frame into fog. Use `threshold ≈ 1.3` plus `instanceColor = a × 2.2–2.4` on additive pools so only muzzle flashes and shell bursts cross it. Additive pools are `toneMapped` by `OutputPass`, so >1 values still resolve to white rather than clipping.
- Post-processing (`EffectComposer` + `RenderPass` + `UnrealBloomPass` + grade `ShaderPass` + `OutputPass`) is **WebGL-only**: the WebGPU build rejects `ShaderMaterial`/GLSL, so `await import(...)` the passes inside `try/catch` behind `MODE === 'webgl'` and fall back to `renderer.render`. Composer path costs ~10–20 % fps on the software rasterizer (`?fx=0` disables it). The same split bites the particle fade: `onBeforeCompile` is ignored by the WebGPU/NodeMaterial path, so the premul smoke loses its per-instance alpha and reverts to dark smears there. Scale the puff texture's alpha down on that build (`const FXA = MODE === 'webgl' ? 1 : 0.5`) — it is a fallback, and additive pools are unaffected because their fade rides on rgb.
- Wispy smoke beats a radial gradient: build the puff as `ImageData` = value-noise fBm × a soft radial mask (`puffTex()`), or every puff reads as an identical bubble. Perturb the mask *radius* by the noise (`core = clamp((1.06 − dist·(0.6+0.7n))/0.55, 0, 1)`) plus a `guard` term so the alpha never reaches the quad edge — a clean circular rim is the tell that the radius is unmodulated.
- **A shell trail must be emitted by distance, not by timer.** Fixed-interval emission gives bead spacing `v·dt`; at 32 m/s that is ~1.6 m between 1.1 m puffs, so the arc reads as "beads on a string". Accumulate travelled distance and emit every ~1.3 m with a growing/faint puff (0.75 → 2.7 m, opacity ~0.34) so consecutive puffs overlap into one wispy streak at every muzzle velocity. Keep a shorter `ttl` (≈1.25 s) so the trail does not consume the whole smoke pool.
- One `InstancedMesh` per pool means **raising `count` costs no draw calls** — only a little CPU in the per-frame matrix sync. Budget capacity from the worst-case concurrent particle count, and remember a full pool makes `emit()` return `false` *without* consuming `vrnd()`, which shifts the effects stream (harmless for gameplay, but it will change effect layouts and counts).
- With `autoReset = false` on `renderer.info` and one `info.reset()` per frame, `info()` reports the **whole frame** including every composer pass and the shadow pass — the only numbers comparable across configurations.
- **Prove PRNG separation, don't assume it.** All effect randomness (pool spin/rotation, spread, crater size, hoof dust) reads a second stream `vrnd = mulberry32(0x9D3C71)`; gameplay keeps `rnd`. Test: copy the file, patch a constant, step both to the same `t` with `?pause=1`, and compare a **hash of the gameplay fields only** — `[t, phase, over, winner, shellsInFlight, units, log, air craft positions/hp/state, air losses, bombs dropped]`. Particle counts are *allowed* to differ; the battle must not. Including the aircraft state is what makes the probe bite now: those positions are `rnd`-driven, so a leak into `vrnd` shows up immediately. Two probes, both worth running: (a) a pure texture-colour change must give a **byte-identical** `state()` including counts, and (b) **shrinking a pool's `count`** (e.g. smoke 512 → 200) makes `emit()` starve, so the effects stream genuinely diverges — counts move — while gameplay stays fixed. That second probe is the real proof; a visual-constant probe can pass by accident. Add a third that flips a **visual knob inside the combat path** — e.g. tracers per burst `3 → 5` — and require gameplay to stay bit-identical: it is the probe that catches `rnd()` hiding in visual code, and it only passes once the spread is drawn from `vrnd`. Doing this caught a real leak — raising pool capacity changed how often `emit()` found a free slot, which changed how many `rnd()` draws happened, which changed the battle. Splitting the streams changed the outcome once (union still wins, ~41.8 s); after that, effect retunes are free.

## Air / emplacement layer (verified in `civil-war-battle.html`)
- **战壕 (trenches) — the cross-section *logic* makes it a trench, not the silhouette.** A work needs all four elements in order: **parados** (rear bank, crest 0.74 m) → **ditch floor at grade** (the men stand between the banks) → **fire step** (0.52 m) → **parapet** (crest 1.30 m ≈ shoulder height). Build it as one 8-row `BufferGeometry` ribbon per line, per-vertex colours (ditch faces and inner slopes darkened ≈0.38·k, crests 1.0) and UVs baked against a dirt `map`. Then the fittings: a **headlog** resting on the parapet with a firing gap under it, sandbags on the crest, revetment stakes on the **ditch walls** (not loose in the walkway), abatis 3.5–4 m in front, and **traverses** every 20–40 m (earth walls perpendicular to the parapet, crown just below it) against enfilade. Two lines = 12 draw calls. Flip the triangle winding per facing (`idx.push(a, c, b, …)` vs `(a, b, c, …)`) or the mirrored ridge's normals point down. The ground plane is 128 segments (≈6.1 m/quad), so a real 2.5 m excavation is **not representable** — build the above-grade breastwork the 1860s sources describe and say so in the prompt.
- **An earthwork also needs a *traversal attribute*, or units pass through it as if it were flat ground.** Derive a height field from the *same* section data the mesh is built from — `workH(x, z)` interpolates between the two adjacent rows at the queried signed `dz`, minus natural grade — and drive two things with it: (1) every soldier's `y = groundY(x, z) = terrainH + workH`, so crossing the parapet *lifts* him over the bank instead of clipping through it (the front rank visibly straddles the crest); (2) a passage cost multiplied into the unit's movement, `u.spd = nominal * workTraverse(kind, x, z)`, differentiated by arm: infantry `1 − 0.72·clamp((h − 0.15)/1.0)`, cavalry `1 − 0.92·clamp((h − 0.10)/0.9)`, floored at 0.25 / 0.05, then × an abatis factor (`1 − 0.35·ab` foot, `1 − 0.78·ab` horse). Measured: crossing 4.5 m of work takes **5.02 s instead of 1.61 s** nominal, hitting 0.28 (foot) / 0.08 (horse) at the 1.30 m crest. Without it the parapet is only a texture — both arms cross at full speed.
- **The three cover rules — every one of them was inverted at first.** Cover requires (1) *position*: signed distance from the work centre in `[-3.0, +1.5]`, enemy-positive, i.e. on the ditch/fire-step side — **not** a symmetric ±7 m band, which also credits the open ground *in front of* the parapet; (2) *direction*: only fire arriving from the parapet side counts, so enfilade and rear fire get nothing (`coverAgainst(tgt, shooterZ)`); (3) *not inside a sally port*: the parapet is deliberately lowered where the assault crosses, so the gap has no cover either (`1 − 0.85·open`). Units must also be **placed** in the ditch by the same function that builds it — `trenchDitchZ(key, x) = Z + (wob(x) − 0.175)·facing` — because hand-tuned start `z` values leave a whole unit 3 m outside its own work. Sally ports belong *between* units, never in front of one.
- **Sun-lit earth blows out white**: the sun is 2.6 + hemi 1.15 + ambient 0.34, so a bare 0.45-albedo face clips to near-white and the earthwork reads as a pale wall. Multiply a dirt map (≈0.49) by vertex colours around 0.8 — not 1.0, and not "no map".
- **Aircraft and AA guns use a `RigPool`**: one `InstancedMesh` per part shared across *all* instances of that type (6 fighters = 8 draw calls total, not 48). Per-part `dyn` keys (`'yaw' | 'barrel' | 'prop'`) animate turrets/props; `local.rotation.order = 'YXZ'` so `'barrel'` composes traverse-then-elevate. **Look up `mats[def.mat]`** — passing the key string instead yields `material = 'skin'`, and three **silently skips the mesh** (`material.visible` is `undefined`) with no error, no warning, correct instance matrices, and nothing on screen. Diagnose this class of bug by reading `mesh.material.type`, not by trusting that the geometry is in the scene.
- **Prop discs sell "engine running"**: a thin `cyl(1.5,1.5,0.02,20)` rotated into the flight plane (`rotateX(π/2)`) with `MeshBasicMaterial` at ~0.11 opacity, plus crossed blades that actually spin.
- **Turn radius = speed ÷ yaw rate.** A bomber at 50 m/s with a 0.20 rad/s rate turns in 250 m, so it can never hold a 172 m orbit — it spirals outward forever. Derive the rate from the orbit you want (0.42 rad/s for 172 m).
- **Mutual pursuit runs away on two axes.** Two fighters each aiming at `target.y + 3` climb forever, because each is always aiming above the other; clamp the vertical aim to ±30 m of the pursuer's own altitude. Horizontally they fly off the map, so leach them (break off pursuit beyond ~290 m from the field centre) and cap altitude (`ALT_MAX = 250`).
- **Never route a falling craft through `moveCraft`'s altitude floor** (`if (a.y < ALT_MIN) a.y = ALT_MIN`) — it hovers at 62 m and never crashes. Integrate the crash dive separately, without clamps.
- **A bomber must release on the *predicted impact*, never on its own position.** The bomb inherits the aircraft's full forward speed (~49 m/s) and falls ~150 m, so the release point is ~270 m short of the target. A gate that tests the bomber's own `z` (the first version) throws every stick onto empty grass — 40 bombs dropped, **zero** casualties, while the art, physics, craters and explosions all looked perfect. Nor can a *circular* pattern be rescued by retuning the gate: for a tangent-thrown bomb the miss distance is `sqrt(2R² + L² − 2R√(R²+L²))` (≈147 m at R=175, L=270), so no phase of the orbit lands on the line. Bombers fly a **straight racetrack** instead — two legs `±380 m` along z, `190 m` apart laterally — and release a stick of 4 when `|bombLead.z − tz| < 26` (then a 22 s cooldown). Verify by counting hit messages, not by looking at the bombs.
- AA solves `p + v·(d/190) − ½gt²`, fires only within ~0.09 rad of that, and schedules the burst at the flight time — **the burst, not the tracer, is the visual**. Carry the firing `side` on the fuse entry: the fuse point is the *target's* future position, which a friendly fighter chasing that same aircraft routinely occupies, so a burst without a side test shoots down your own planes.
- Lethality lives in a few constants and they were all far too high at first (6/6 fighters down in 20 s). Working values: flak 10 % × 12–22 hp inside 10 m, fighter guns 16 % × 4–10 hp per 0.30 s burst, bombs ≤3 men each inside 8.5 m.
- **An airfield is a sortie cycle, not a spawn point**: `parked → taxi → roll → climb → patrol/bomb` and, when damaged (hp < 30 %) or the battle ends, `rtb → final → flare → rollout → parked`. Two rules make it behave: (1) **flatten the pad inside `terrainH`** (blend toward the natural height sampled at the field centre, with a 30 m falloff) — a runway laid on 2.6 m rolling terrain makes the ground roll read as a boat at sea, and the same function keeps soldiers/AA on the pad consistent; clear trees with an `onAirfield()` test. (2) Give the ground states a `GND = 0.55` lift so gearless models look like they are on wheels.
- **The re-launch loop needs a brake.** With `launchAt` compared against `B.t`, a landed aircraft instantly taxis again, so after the battle they keep sortieing and shooting each other forever — the loss tally silently climbed to 10/10 while 8 aircraft were still flying. Gate the launch on `!B.over`, set `launchAt = B.t + 16` on touchdown for a turnaround, and gate AA and fighter gunnery on `!B.over` so the air war winds down with the battle.
- **Lower/slower is better for spectacle, but it moves the bombing geometry.** Fighters 46 m/s at 58–86 m and bombers 34 m/s at 76–90 m (`ALT_MIN 26`, `ALT_MAX 120`) read far better than 66 m/s at 120–170 m — but the ballistic throw is `L = v·√(2h/g)`, so dropping from 66 m/s @ 150 m to 34 m/s @ 85 m cuts the lead from ~270 m to ~141 m; re-derive the release gate and `BOMB_RUN` when you touch either number.
- **Shell damage should be two-stage, and fragments need their own pool.** Direct blast (`SHELL_KILL_RADIUS 6.4`, cap 8, 85 %) plus a **fragment ring** (`15.5 m`, cap 4, 20 %) — same `blastCasualties` helper, two calls. Visually, a shard pool is just the billboard pool with `buoy: -15` (gravity) and a sliver texture: 16 shards per shell at 7–21 m/s with 3–10 m/s of lift arc for ~1 s. Add a **scorch decal** (bigger, softer, darker than the crater, `renderOrder 0` under it) for the "slight ground damage" the crater alone does not sell.
- **Random battlefield obstacles need a spatial hash, because `groundY` runs per soldier per step.** ~140 obstacles × 470 soldiers × up to 8 substeps is ~34 M distance tests/s with a linear scan; an 8 m grid (`obNear`) makes it O(1) per query. Place them with their **own PRNG** (`ornd = mulberry32(0x0B57AC1E)`) so the layout neither consumes `rnd` nor is perturbed by visual retunes, and feed the same two attributes as the earthworks — height into `groundY`/`workTraverse` (slows crossing, lifts men) and a cover value into `coverAt`. Keep obstacle heights at 0.46–0.86 m so clambering over them stays plausible. The decoupling is probeable: doubling the mesh `sc` must leave `state()` byte-identical (it does).
- **"Many elements are invisible" has three usual causes; check them in this order.** (1) *Camera inside the traffic pattern*: the overview view sat at y = 86 m while cruise is 58–90 m and the new airfield lies underneath it, so a 23 m-span bomber passed **22 m** from the lens and filled half the frame — put spectator cameras **above `ALT_MAX`** (the default view is now y = 140) or outside the launch/climb lane, and keep the runway behind the army's rear. (2) *Fog range vs scene extent*: `Fog(c, 140, 780)` was tuned when all content was within |z| ≤ 120; after airfields moved to |z| = 185 (runway to 263) and the obstacle/tree scatter grew, everything past 140 m was blended toward the sky colour. The shader is `smoothstep(fogNear, fogFar, viewDepth)`, so **`fogNear` must sit outside the play area** (now 260/1350) or distant-but-important geometry simply reads as sky. (3) *Stale `InstancedMesh` bounds*: `Frustum.intersectsObject` calls `object.computeBoundingSphere()` only while it is `null`, and three never invalidates it — so any instanced mesh whose matrices change after the first frame is culled against a frozen sphere (usually the degenerate scale-0 sphere from construction) and vanishes as the origin leaves the frustum. Every *dynamic* instanced mesh must set `frustumCulled = false`. Diagnose all three with `__battle.census(minFog)`, which re-runs three's own frustum test per object and reports `drawn` / distance / fog factor: a healthy default view returns **zero** `drawn` rows above ~0.12 fog.
- Coplanar ground decals (crater, scorch) need `polygonOffset`, not just a few cm of lift — a 2.5–4 cm offset is within depth-precision error at range and the decal flickers or disappears.
- **A "game AI" layer is a think-tick over the existing state machine, not a rewrite.** Every `AI_TICK = 2.4 s` each army scores enemy units (loss × 2.4 + shaken × 1.5 + proximity × 0.7) to pick a **focus target** for converge-fire, nominates a **flanker** (highest morale) and a **reserve** (most intact), commits the reserve when the enemy is shaken (`foeMorale < 0.62`) or a friendly unit is under 45 %, and flips to a **hold** posture when its own average morale drops below 0.34 (holding units keep firing instead of auto-charging). Orders are consumed by `unitUpdate` via `u.order`: `reserve` parks behind the line, `hold` stops at |z| > 40, `flank` drifts laterally toward `ai.flankX`, and alternating `fire`/`advance` orders stagger the engagement range (98 m vs 62 m) into bounding overwatch. Two traps: keep every decision **PRNG-free deterministic scoring** (it must not perturb the `rnd` stream), and key the bounding alternation off the **roster index parity**, not the per-tick sorted list, or units flip between orders every tick and jitter on the spot.
- All of it is stepped from `simulate()` (physics time), and **anything that can change the outcome draws `rnd`, never `vrnd`** — spawn positions, orbit angles, aim, bomb-release jitter, damage rolls. Only puffs, smoke and tracer fade use `vrnd`. This includes values that merely *orient* a visual: the per-tracer deviation spread looked harmless but sat in the same loop as the damage roll, so drawing it from `rnd` meant changing tracers-per-burst shifted the whole battle.

## Rescaling the battlefield (measured in `civil-war-battle.html`, `S = 4`)
- **Scale the *layout*, never the units.** A single `S` multiplies every spatial constant (frontage, army separation, artillery/airfield depth, tree ring radius, obstacle scatter, camera positions) while soldier/aircraft/vehicle sizes, weapon ranges, kill radii and effect durations stay put — scaling those too is just a change of units and looks identical.
- **Everything derived from the extent must be rescaled with it, or it silently breaks**: `terrainBase`'s flat inner region (or the hills start inside the battlefield), ground plane size **and segments** (3120 m at 128 segments is 24 m/quad — the airfield pad flattening disappears), `scene.fog` near/far (a near plane inside the play area washes out everything past it), `camera.far`, the shadow camera bounds **and** `mapSize` (±680 m at 2048 is 0.66 m/texel → 4096), texture `repeat` (the ground map is one tile across the whole plane), tree/obstacle **counts** (16× area with 4× objects = a visibly empty field), AI distance thresholds (`hold`/`reserve` lines, artillery search range, flank offsets), air patrol/racetrack radii and `BOMB_RUN`, and the rout exit bound.
- **The infantry advance speed has to rise with the depth** or the armies spend 90 s walking: 2.8 → 4.2 m/s at 4× depth, with the soldier animation cap raised to match.
- **A wide front needs a rout cascade or the melee never ends.** With 8 units spread over 736 m, one unit breaking no longer unhinges its neighbours, and the battle ground on for **250 s+** of local slugging. Adding a decaying shock wave to friendly units within 300 m of a rout (×0.26, linear falloff) collapsed the line in waves and brought it back to ~120 s.
- **Rout speed must be *below* charge speed** (5.6 vs 7.5 m/s). At equal speed a charging unit chases a routing one forever and both leave the map — this showed up as units frozen in `charge` for 150 s with an unchanged headcount. Re-targeting also must skip `state === 'rout'` targets.

## Armour / motorised layer (measured in `civil-war-battle.html`)
- **Tanks live outside `U`/`C.units` on purpose**: musketry casualty code only walks unit rosters, so armour is immune to volleys by construction, and only shells/bombs (`damageTank`) can hurt it. Give artillery a tank-priority target (`gun.tank`, +range) so the counter exists, and let a destroyed tank stay on the field as a **baked-blackened wreck** (re-`paint()` the rig) instead of vanishing.
- **The tank's job is morale, not kills**: a `shock` aura (`+2.4/s` scaled by proximity, friendly units get `−1.2/s`) inside 54–78 m breaks the trench line the way WWI tanks did. Armour crosses the earthwork at only ~35 % penalty (infantry 72 %) — a tank that cannot cross a parapet is useless.
- **Wheels/axles obey the same rig rule as propellers**: a part rotates about its *own* origin, so wheels spinning about the part origin swing around the vehicle. Build **one part per axle** whose origin lies on the axle line, with the left/right wheels offset only along x (invariant under the x-rotation) — then a `dyn: 'wheel'` part spins in place. The truck has 3 axles, the motorcycle 2.
- **Motorised reserve = a logistics loop, not scenery**: trucks pick the most depleted on-field friendly infantry (`neediest`), drive to it, `reinforce()` up to N men, return to the depot and wait. Two traps: (1) `kill()` **compacts the slot registry**, so a revived soldier must be given a free slot (`slotSoldier`/`soldierSlot`) or it renders on top of a living man; (2) re-target when the destination dies or routes mid-drive, or the truck arrives to an empty field and unloads nothing.
- Motorcycles are couriers: a two-point patrol at 13 m/s that also clamps the army's AI think timer (`ai.t = min(ai.t, 1.2)`) so the command layer reacts sooner where they run.

## Terrain features (airfield / road / river) & hero layer (measured in `civil-war-battle.html`)
- **"看不到机场/道路/河道" 是三类原因叠加，不是"没画"**：(1) **共面贴花没有 `polygonOffset`** —— 道路/跑道只抬高 2–7 cm，在 500 m 外已落在深度精度内，会随镜头闪烁甚至整段消失；材质加 `polygonOffset: true, factor/units ≈ −3…−4`（＋ `renderOrder`）才稳定。(2) **对比度** —— 跑道底色 `#6d6552` 与草色同亮度，从空中看就是草地；改成亮砾石/混凝土色并画粗标线后一眼可辨。(3) **`fogNear` 在内容之内** —— 旧 `Fog(200*S, 750*S)` 把 |z|=740 的机场洗成 0.32 雾；推到 `260*S/900*S` 只让远景变清晰，600 m 内本来无雾、观感不变。再加 `texture.anisotropy = MAXANISO`（`renderer.capabilities.getMaxAnisotropy()`，WebGPU 后端没有该 API，兜底 4）：掠射角下 `anisotropy=1` 会把 26 m 宽的跑道 mip 成一片草色。
- **一条"下沉"的河必须挖进 `terrainBase`，不能用贴花画**：把 `terrainBase` 拆成 `terrainFlat + riverDepth(x,z)`（对河心线 |z−RIVER.z(x)| 的平滑槽），`groundY` / 贴花 / 士兵 y 就自动跟着河床走 —— 河道于是是个真属性。地面网格 8.1 m/格表示不了 26 m 水面的细岸，所以水面/河床另建 ribbon（304 段），河岸才不呈锯齿。水面用 `MeshStandardMaterial` + 滚动 `normalMap`（UV offset 是标准材质 uniform，WebGPU 也成立）；`Water`/`Water2` 是 `ShaderMaterial`，WebGPU 后端直接失败，不能用。
- **河床/岸坡颜色是乘两次的结果**：`map × vertexColor` —— 岸外行用草色、水线用沙色、河心用泥色；贴图底色必须偏亮（`#cbb994`），否则整条 68 m 河谷被乘成黑褐色（第一版就是）。水面半宽必须 < `bank × (1−0.55)` 量级，否则水线落到河床之下、水面反而看不见。
- **浅水要进 `workTraverse`，不能做硬阻挡**：`waterTraverse` 河心 ×0.72（步）/ ×0.55（骑）叠进通行系数，战线才不会卡在河边；实测 180 s 内仍正常以 union 取胜结束。
- **英雄建筑（重型堡垒）**：每方 1 座，2 个 draw call（烘焙顶点色几何）。属性必须真的接线，否则只是布景 —— 3 门要塞炮 → `fireShell`（给它加 `gun.muzzleY` 抬到炮眼高度）+ `explodeGround`；对 48 m 内友军方向性掩护 → `coverAt`；耐久 → `damageFort`，炮弹与航弹两条路径都接（`projectilesUpdate` / `bombImpact`）。选址 **x=±300**：中央 z=∓330 虽是 y=0 的平地，却会糊住两条 26 m 高的中线机位，侧移才不挡镜（不要靠抬高机位躲）。
- **炮台的"攻城弹"闸门不能只靠一个只在开火分支里自增的计数器**：`if (best && seq%4===3)` 一旦 `best` 变 null，`seq` 永不前进 → 永久停火（实测 hp 冻在 t≈45）。改为"无步兵目标时必须允许打堡垒"。实测炮弹能把 1500 → 1264，摧毁后整座压成焦石色（`mat.color`）而不是纯黑剪影。
- **英雄单位（重型战车）**：每方 1 辆、独立 `RigPool`（2 例），`hero: true` 分支把恐惧半径 78 → 132 m、单发 `blastCasualties(13 m, cap 10)`；炮塔用 `dyn:'yaw'` 独立跟踪目标（轻坦也受益），`vehSync` 写 `t.turret`。仍然只有火炮/航弹能伤它（复用 §Armour 的免疫结构）。
- HUD 的 `air` 行与 debug API 都加了 `重战车`/`堡垒`，新增 `__battle.fort()`。新增机位 `战场地形`（侧向剖面，一眼看全河/路/壕线/堡垒/机场）与 `机场`（按钮 6/7，键盘 1–9）。
- **预算**：默认全景 440 calls / 1.129e6 tris（原 417 / 1.117e6），+23 calls / +12 k tris = 河道 2 + 桥 2 + 侧路 4 + 停机坪 1 + 堡垒 2 + 英雄车 4（+ 城堡/英雄车各一份阴影 pass）。确定性探针：`sim(75)` 的玩法哈希两次加载均为 `c5e7e028`；曳光弹 3→5 的视觉旋钮下哈希不变（`9099f831`）、粒子数 1203→1205。

## Draw-call budget / displayed-content reduction (measured in `civil-war-battle.html`)
Measured at the default view, t=30, same visible content: **252 → 238 meshes, 436 → 404 draw calls, 4.76e5 → 4.42e5 tris**.
- **Static batching beats instancing for anything that never moves.** Bake a prop set's instance transforms into *one* merged geometry — `bakedMesh(mat, [{geo, m4, col}])` — so 5 obstacle `InstancedMesh`es became 1, and each trench's 5 fitting meshes became 3. A baked mesh also has **real vertex bounds**, so frustum culling keeps working (unlike a dynamic `InstancedMesh`), and `matrixAutoUpdate = false` skips the per-frame matrix rebuild. **Trap: `mergeGeometries` needs a consistent index state** — `IcosahedronGeometry` is *non-indexed* while Box/Cylinder/Sphere are indexed, so normalise with `toNonIndexed()` first or the merge returns **null** and `new Mesh(null)` throws inside `updateMorphTargets`.
- **Merge rig parts by (material, `dyn` key).** Parts sharing a material that never animate independently are one part with the offsets baked into the geometry (fighter 8 → 6, bomber 11 → 8, AA 5 → 4). Parts that must rotate about their **own** axis (propellers, prop discs, AA barrels) must stay separate — merged, they swing around the airframe centre instead of spinning in place.
- **Cast shadows selectively.** The sun map is 2048 over ±170 m = **0.166 m/texel**, so anything under ~0.5 m renders a sub-texel smudge anyway: drop `castShadow` on sandbags, stakes, abatis, traverses and edge markers; keep it on silhouettes that read (berm, headlog, buildings, vehicles, aircraft).
- **`BatchedMesh` is the researched scale-out path when the object count really grows** — hundreds of *different* geometries sharing one material: one draw call for the batch, plus per-instance `setVisibleAt()` (cull individual instances) and `setGeometryIdAt()` (swap an instance to a lower-detail geometry, i.e. per-instance LOD). Not adopted here: the content is already down to ~30 meshes, and `BatchedMesh` rides the WebGL multi-draw path while this artifact must also run on the WebGPU build. `THREE.LOD` is the per-*object* equivalent and does nothing for instanced content.

## Working method (what actually caught the bugs)
- **Measure, never eyeball.** Every claim in the sections above came from a number: `info()` for calls/tris, `census()` for visibility, the three probes for PRNG separation, a hit-message count for "do the bombs land", a men-count trace for "does the reinforcement arrive". A screenshot proves a scene *looks* right; it cannot prove a feature *works*.
- **A feature that exists but changes nothing is the most common failure**, and it is always the same shape: the art/physics are there but the *attribute is not wired into the simulation*. Three examples from this file, all of which looked perfect on screen: bombs that never hit (release gated on the bomber's own position, not the predicted impact), a trench with no traversal attribute (men walked through a 1.3 m parapet), trucks that unloaded zero men (revived soldiers never re-registered a slot). Before debugging the visuals, print the *effect* the feature is supposed to have on the sim and check it is non-zero.
- **Silent failure classes to check by reading state, not symptoms**: a `material` that is a *string* (three skips the mesh with no error), a stale `InstancedMesh` bounding sphere (whole group culled), a `mergeGeometries` null (index-state mismatch), and a `Math.abs(x - const)` milestone that was already true at spawn. Each has a dedicated index row above.
- **Re-run the probes after every retune.** The three probes (colour / pool-starvation / a visual knob inside the combat path) are cheap and they are the only thing standing between "I changed the smoke" and "the battle silently changed". Determinism is two loads + one hash — do it before claiming done.
- **Rescaling and retuning invalidate hard-coded distances.** When the field, the population or the effect size changes, walk the §Rescale checklist; thresholds that were tuned for the old extent (AI lines, `BOMB_RUN`, patrol radii, rout bounds, fog, shadow map) go wrong *silently* and usually show up as "it feels stuck" rather than as an error.

## Construction-domain layer (verified against `construction-sim`)
- Sequence: `footing → 逐层(柱 → 主梁 → 次梁 → 楼板 → 墙板 → 校验) → 屋顶 → 完工报告`.
- `主梁` along X, `次梁` along Z, **staggered 0.6** in Y so perpendicular beams never share a corner volume.
- Wall panels leave **0.1 m clearance each end**.
- Tower crane hierarchy: `base → slewing(θ) → jib → trolley(r) → hookGroup(cable.scale.y)`. Drive by polar `(θ, r, h)`.
- Per-axis speed-limited easing (`vT≈0.85, vR≈5.0, vH≈8.0`); hoist **only after** slew/radius are near settled.
- Release only when crane settled **and** horiz `< 0.07` and vert within `0.2`; then `kinematic → dynamic` drop. `SETTLE` = ~42 physics steps (60 Hz × 0.7 s).
- Component state machine: `DELIVERED → TO_PICK → ATTACH → LIFT → TRANSIT → LOWER → SETTLE → VALIDATE → FASTEN`.
- Placement verdict: `<0.08 m` OK, `0.08–0.25 m` WARN, `>0.25 m` or rot `>5°` RESEAT.
- Check support logic (柱有基础、梁端落柱、板落梁) and no interpenetration.
